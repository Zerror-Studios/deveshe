## 0. Workspace rules (shared by every ZCommerce repo)

This repo is one part of the ZCommerce platform. The full map is in the workspace root `../CLAUDE.md` (`../../CLAUDE.md` for storefronts), when that file is present. The rules below are mandatory here even when it isn't.

1. **PRD first (tiered).**
   - **T1** covers: a new feature, page or module; a GraphQL contract change; a model or event change; auth, tenant, permission or billing logic; a new integration. T1 needs a PRD in `docs/prd/` with **Status: Approved** before any code. If none exists, draft one from `docs/prd/_TEMPLATE.md` (Status *Draft*) and **stop for approval**.
   - **T2** covers bug fixes, tweaks and small refactors. T2 needs only a line in `docs/changelog/YYYY-MM.md`.
   - Unsure of the tier? Treat it as T1 and ask.
   - Cross-repo PRDs have their source of truth in `zcom-backend/docs/prd/`; consumer repos keep a pointer PRD.
2. **Read docs before, update docs after (MANDATORY, no exceptions).** Documentation is part of the definition of done. Every change, including code, config, infra, dependencies and decisions, updates all related docs in the same change. Record decisions and approvals from conversation in the PRD or ADR immediately, before implementing. A task isn't finished while any doc disagrees with the code.
   - **Before** a change, read this file, `README.md`, `docs/README.md`, and the relevant PRD, ADR and architecture docs.
   - **After** it, in the same change, update whatever is now stale: the README (setup, commands, env names), `docs/architecture/*` (contracts), PRD status and implementation log, the changelog, `docs/README.md` (the index), and this `CLAUDE.md` (rules and known issues).
   - End every task with a **"Docs impact"** line.
3. **Ask, don't guess.**
   - Ask one precise question, with options and a recommendation, when the request conflicts with a PRD, an ADR, this file, or the code.
   - Do the same when docs and code disagree, or when a change would affect a contract, a security or tenant boundary, the design system, dependencies or deployment.
   - Don't ask about things you can verify in the code yourself.
4. **Scoped and safe.**
   - No drive-by refactors or mass reformatting.
   - Don't add dependencies without asking.
   - Never commit, push, deploy or touch databases unless asked.
   - Never print or commit secrets or `.env` values, including the token embedded in `git remote -v`.
   - Report checks honestly, keeping pre-existing failures separate from new ones.
5. **Coding style: the owner's signature (mandatory).** Follow the workspace `CODING_STYLE.md` (`../CODING_STYLE.md`, or `../../CODING_STYLE.md` for storefronts). Its baseline is the `zcom-backend` style.
   - 2 spaces, double quotes, semicolons, trailing commas, 80 columns.
   - Named exports with barrel `index.ts` files (React page and component files are the exception: `export default X;` at the end).
   - File names are `kebab-case.role.ts`.
   - Static-class controllers and services, with `return await`.
   - `xEnum = {…} as const`; the `I` prefix only for Mongoose documents; `UPPER_SNAKE` constants with unit suffixes (`_MS`, `_DAYS`).
   - `GraphQLError` with `extensions.code`; one `createLogger({ service })` per module.
   - JSDoc module headers and `// ─── ` section dividers.

   **New files** follow it exactly. **Edits** keep the file's existing formatting; never reformat untouched code. When you commit, use Conventional Commits: `type(scope): summary (PRD-NNN)`.
6. **Storefront specifics.**
   - Use only backend operations listed in the storefront contract doc, and validate field-level.
   - The server computes money.
   - **Plumbing is the kit's** (`@zcom/storefront-kit`, kit PRD-002): the proxy, Apollo links, customer session, guest cart id, consent, tags, attribution, payment launch and return, server reads and security headers. Fix them in `../../zcom-storefront-kit` (every store gets the fix with the next tag), never with a local copy. When you fix the store's own shared logic (`utils/api-error.util.js`, `utils/sanitize-html.util.js`, `hooks/useVisitor.jsx`, the checkout view, the stores), check `../rare-element` for the same issue.

## 1. What this is

The **Deveshe Dreams** brand storefront: a custom-designed shopper site on ZCommerce, with home, products, lookbooks, cart, checkout (the store's payment app: Razorpay, Cashfree or PayU, PRD-011; Nimbbl until its 2026-11-15 shutdown, backend PRD-029 D1), login and profile.

**Stack:**
- Next.js 16 with the **App Router** (since 2026-11-11, ADR-001), React 19.3, **JavaScript**.
- Apollo Client 4, zustand 5, react-hook-form + zod 4.
- GSAP 3.15 from the public npm registry (every plugin free since 3.13) with ScrollTrigger, SplitText and ScrollToPlugin (`gsap/dist/*`).
- `lenis` 1.3 (its own `autoRaf` loop), Swiper 14, react-toastify, three 0.187 / @react-three/fiber 9 / drei 10 (only the contact `PhoneModal`, loaded with `ssr: false`). Package versions follow the shared table in kit PRD-002 §11 (D3).

MUI, emotion, styled-components (PRD-002 SF-21), `react-tooltip` and `cross-fetch` (re-audit RMAINT-9) were removed, and the lockfile is pruned.

**Integration status: on the current backend contract (PRD-002 WS-F2, 2026-10-14).**
- All 58 operations validate against the composed backend schema (2026-11-11, after the App Router move) (PRD-032 added 12 review operations and `sort` on `GetProductReviews`; PRD-020 FR-13 added `GetVariantAvailability`; PRD-015 FR-20 added `MyOrderDetail`, `CancelMyOrder`, `CreateReturnRequest` and `CancelMyReturnRequest`; PRD-014 FR-0.8/FR-0.9 added `getClientSideCategories` for the category listing and `getReviews` for the home reviews, and `pricing` on the checkout session; FR-2.8 added `SubscribeNewsletter`, `GetProductReviews` and `GetSitemapProducts`; round 2 added `issueGuestCartId` and `mergeGuestCart`; round 3 added `unsubscribeNewsletter` for the `/unsubscribe` page; PRD-003 FR-0.5 added `customerRequestPasswordReset` and `customerResetPassword` for `/forgot-password` and `/reset-password`). The backend builds the link from the tenant's **configured domain**, so that domain must serve this storefront or redirect keeping the query string (FIN-3; the owner checks it per tenant). The contract is `../../zcom-backend/docs/architecture/storefront-api-contract.md`.
- **Tenant by host** (the backend has no db-token, PRD-007): the browser calls same-origin `/v1/graphql`, which `src/proxy.js` (the kit's `createZcomMiddleware`, kit PRD-002 FR-4.1) proxies to `API_GATEWAY_URL`. The kit strips client `x-zcom-*`, `x-tenant-domain` and `x-forwarded-host` headers (VSEC-4) and the shopper's `Origin`/`Referer` (PRD-007 FR-8.2), and adds the **edge headers**: `x-zcom-client-ip`, `x-tenant-domain` and `x-zcom-edge-secret` (PRD-002 R2-C1). The gateway accepts the tenant only with the edge secret, so `EDGE_SHARED_SECRET` is required in production (PRD-007 FR-8.3). The client IP (VSEC-3) is Vercel's `x-vercel-forwarded-for` on Vercel (D9); off Vercel only a header named in `trustedIpHeader` is used (none is set, so no IP is sent; the right-most `x-forwarded-for` fallback of the store's own proxy is gone). Without `NEXT_PUBLIC_TENANT_DOMAIN` the proxy fails closed (never an untenanted request). Server reads (the server pages `/`, `/shop`, `/shop/[categories]`, `/search`, `/blogs`, `/blogs/[slug]` and `/product/[slug]`, the sitemap; `lib/server-query.js` on the kit's `zcomFetch`) send the tenant and the edge secret but no `x-zcom-client-ip` (catalog reads), except `/pay/[token]`, which sends the shopper's IP (`getRequestClientIp`).
- **Newsletter unsubscribe (PRD-002 VCON-1):** `/unsubscribe` (`views/UnsubscribeView.jsx`, `noindex, nofollow`) is the target of the link the backend puts in campaign emails (`https://<tenant domain>/unsubscribe?email=…&token=…`, signed with `NEWSLETTER_TOKEN_SECRET`). It reads `email` and `token` once, removes them from the URL (`history.replaceState`, shallow), and calls `unsubscribeNewsletter(email, token)`. The server answers uniformly, so every server answer shows the same neutral message; only a network failure offers a retry.
- **Guest cart ids are server-issued** (`issueGuestCartId`, `<random>.<hmac>`), requested lazily by `useVisitor` on the first add to bag; on `INVALID_GUEST_ID` the stored id is dropped and the call retried once. Old unsigned UUIDs are dropped on read, so **existing guest bags are lost once** at deploy.
- **Checkout requires login** (the backend checkout operations are customer-only); the guest bag is moved in at login with one `mergeGuestCart` call (server-side, idempotent).
- **Backend gaps shown as such:** change password (logged in) and account deactivation are hidden, while a forgotten password is reset through `/forgot-password` → `/reset-password` (PRD-003 FR-0.5); "Unavailable / Notify me" shows for an ARCHIVED variant, an option combination with no published variant, or a `PRODUCT_UNAVAILABLE` answer (PRD-014 UX-09, as rare-element), and "Sold out / Notify me" for an `OUT_OF_STOCK` variant.
- **Stock signal (PRD-020 FR-13, 2026-10-26):** `Variant.availability` / `availableQuantity` and `Product.availability` drive the PDP (struck-through sold-out choices, "Only N left" / "Low stock"), the card badges and the bag (sold-out lines hold checkout); the PDP and the bag re-read with `getVariantAvailability` (`hooks/useVariantAvailability.jsx`). **`null` renders exactly as before** (signal off by default per store). "Notify me" works for guests with an email (also in the mobile bag bar); since CP-22 a guest's alert starts only after the emailed link to `/back-in-stock/confirm` is opened (`utils/back-in-stock.util.js`, twin of rare `utils/back-in-stock.js`), so a guest sees "check your email to confirm" and signed-in shoppers keep the old copy; `RATE_LIMITED` shows neutral copy.
- **Order page (PRD-015 FR-20, 2026-10-26):** `/profile/orders/[id]` shows `displayStatus`, tracking (`shipment.trackingUrl`, no hard-coded Shiprocket link), Cancel when `canCancel` and returns; the profile order table links to it.
- **Catalog (live design merged from `main`, 2026-11-11):** `/shop` and `/shop/[categories]` (`lib/page-data/shop.server.js` + `views/ShopView.jsx`) load every published product of the store or category (pages of 100, capped at 500) and filter in the browser (`context/ShopFilterContext.jsx`, `utils/productFilters.js`), as the live site does; an unknown category is a 404. `/products` and `/category/[slug]` are permanent redirects to them (query kept); `/search` keeps the paged `ProductListing`. The home "Top Picks" are the first 8 products of the `basically-iconic` category, found by slug; no category id is hard-coded anywhere (`test/catalog-listing.test.mjs`). The home "Happy customers" section shows approved `getReviews` results; while the store has none it shows the live site's four customer quotes (`STORE_TESTIMONIALS` in `components/home/ReviewSection.jsx`; PRD-014 D31, owner 2026-11-11, an exception to UX-35 / FR-0.9).
- Nothing has been tested end to end against a running backend or any payment sandbox yet.

## 3. Rules

- **Routing (App Router since 2026-11-11, ADR-001).**
  - One `app/<route>/page.jsx` per route, a **server** file: `metadata` or `generateMetadata` (from the page's `meta` object through `lib/seo-metadata.util.js`; the canonical is the route's path or `meta.canonical`, never with a query), `<PageSchemas meta path />` for the JSON-LD, then the page's client view from `views/`.
  - A page that needs data reads it in a server-only loader (`lib/page-data/<name>.server.js`), returns `{ props }` or `{ notFound: true }`, is read once per request through React `cache()` (keyed by value) and sets `export const dynamic = "force-dynamic"`; unknown or unpublished products are `notFound()`.
  - Client code uses `next/navigation` (`useRouter`, `usePathname`, `useSearchParams`, `useParams`); a static page whose view calls `useSearchParams` wraps it in `<Suspense>`. Pages that read a link token once read `window.location` in their mount effect and drop it with `window.history.replaceState` (a shallow replace).
  - A server file never imports a "use client" file for a value (it gets a reference, not the value): shared constants live in plain modules (`components/listing/listing.constants.js`, `utils/search-term.util.js`).
  - Don't add `src/pages` back.
- **Data.**
  - Put gql documents in `graphql/queries` or `graphql/mutations` and export them through `graphql/index.jsx`. Don't write inline `gql` in components.
  - **One Apollo client, the kit's** (`ZcomSsrProvider` in `components/layouts/Providers.jsx`): the store's own `useQuery` / `useMutation` share it (`@apollo/client/react`), so never create another client or call the gateway by another URL. `context: { skipAuth: true }` sends a call anonymously. Server code reads through `lib/server-query.js` (`serverQuery`, or `createServerQueryClient()` for Apollo's `query()` shape), never a browser client.
  - **The edge secret stays on the server.** The kit reads `EDGE_SHARED_SECRET` only in the proxy and its server functions; import `@zcom/storefront-kit/server` and `lib/*.server.js` only from server files (server pages, route handlers, loaders), never from a "use client" file. Check `.next/static` for the secret after a build.
  - Show errors with `utils/api-error.util.js`, which branches on `extensions.reason` / `code`, never on message text. It maps the round 2 reasons too (`CHECKOUT_EXPIRED`, `RESERVATION_RELEASED`, `INVALID_QTY`, `TOO_MANY_LINES`, `ORDER_CANCELLED`, `INVALID_GUEST_ID`, `TENANT_NOT_FOUND`).
  - The kit's error link: `TOKEN_EXPIRED`/`UNAUTHENTICATED` → refresh once and retry; `INVALID_AUTH_TOKEN`, `TENANT_MISMATCH` or a refused refresh → the session ends (`tokenManager.onSessionEnded`, the auth context shows "Your session has ended"); `TENANT_NOT_FOUND` → `onStoreUnavailable` (one "store unavailable" toast, PRD-002 R2-C5); `TENANT_SUSPENDED` → one reload a minute to the 503 page (PRD-018 FR-1.6). A refresh that fails for a transient reason (network, 5xx) doesn't log the shopper out (RBUG-19).
- **Auth and tokens.**
  - The kit owns the session (kit PRD-002 FR-4.1): the access token lives **in memory only** (the kit's `tokenManager`). The refresh token is the HttpOnly `__Host-zc_cust_rt` cookie (`zc_cust_rt` in dev); JavaScript never reads or writes it, and never selects `refreshToken` from a response.
  - Login, signup (CONFLICT → "account exists") and logout go through `context/AuthContext.jsx` on the kit's `useAuth`: the kit refreshes single-flight, clears the Apollo store before the customer token is used, and merges the guest bag once (`mergeGuestCart`; `merge: "failed"` shows "Some items from your bag are no longer available."; an invalid guest id is dropped). Don't add storage keys.
  - The persisted `isLoggedIn` flag is only a hint that a cookie session may exist; the server decides.
  - The persisted auth store holds no PII (PRD-014 FE-12, as rare RSEC-11: `partialize` to `{ isLoggedIn, userId }` + a v1 migration that rewrites the old `user-data` entry without the profile); `context/AuthContext.jsx` reloads the profile from `getMyProfile` after a page reload.
  - The kit's `migrateLegacyStorage` moves the pre-kit keys once (the `user-data` sign-in hint, the `visitorId` guest bag, the `zc_consent` choice and the `zc_ad_clicks` click ids), so returning shoppers stay signed in and keep their bag and consent. The legacy JS `refresh_token` cookie is not forwarded (kit PRD-002 D10).
  - After login, redirect only through `utils/redirect.util.js`, never `router.back()`. It resolves `?next=` with `new URL` and keeps it only when it stays same-origin (backslashes and control characters rejected, RSEC-6); with no valid `next` the shopper goes to `/`.
- **Money and checkout.** The server computes every price and total; show `getCart` / checkout-session values. Checkout is `createCheckoutSessionFromCart` (with the kit's `buildAttribution()`: GA cookie ids and the visit's UTMs, captured by the kit, PRD-012; only with analytics consent, W1V-C-03, and `buildCheckoutConsent()`) → poll `getCheckoutSession` until RESERVED → `completeCheckout` → `createPaymentSession({orderId})` → `openPaymentCheckout` (`utils/payment-checkout.util.js` on the kit's `launchPayment`, PRD-011: Razorpay / Cashfree SDK windows, a redirect or the PayU or CCAvenue (backend PRD-040, kit 1.0.6) form post, only to the known payment hosts; Nimbbl until its 2026-11-15 shutdown (backend PRD-029 D1: the kit's `launchPayment` opens the store's own `nimbbl_sonic`, registered in `components/layouts/Providers.jsx` with `registerNimbblCheckout`)) → `verifyPayment` → the thank-you page polls `myOrder` until PAID. PayU and Cashfree redirects return through `app/api/payments/return/route.js` (the kit's `paymentReturnHandler`: 303, relative `Location`, PayU's order as `order`) to `/checkout/payment-return`, which verifies through the kit's `usePaymentReturn` with the shopper's session. A retry reuses the unpaid order: its id is kept in sessionStorage with a fingerprint of the cart lines and coupon (`utils/pending-order.util.js`, RBUG-8) and, since VBUG-4, of the checkout details (email + shipping + billing address as sent), also across a reload. A changed bag or coupon starts a new order so the total is never stale (RBUG-9), and so does a changed email or address; a legacy entry without the details fingerprint is never reused. `CHECKOUT_REPLACED`, `PAYMENT_NOT_CONFIGURED`, `MISSING_PROVIDER_ORDER` and `INVALID_EMAIL` have messages in `utils/api-error.util.js` (VCON-2). The coupon controls are locked while an order is being placed or paid, and the pay button stays disabled until the payment window's result or close (RBUG-15). A checkout session takes a 15-minute stock hold, so it is opened for pricing **only on an explicit shopper action**: "Show final total" at the shipping step (same validation as "Pay now") or "Pay now", never on page load, a preselected address or typing (PRD-014 W0V2-02). The summary and the shipping step then show the session's server `pricing` (subtotal, discount, shipping, tax, total); "Pay now" with unchanged details sends the same variables and the backend returns that same active session (R2-C8). Any change to the email, addresses, bag or coupon drops the confirmation and the pricing, and a new session (which replaces the old one and releases its hold) is opened only when the shopper confirms again (PRD-014 UX-03, W0V-C-03, W0V2-02). Without pricing (not confirmed yet, calculating, or a kept order whose details were changed) shipping reads "Calculated at payment" / "Calculating…" and the total is labelled "Total before shipping" (or "Estimated total" with free shipping), never as final. The kept order's entry also holds its checkout session id, so a reload or a retry shows that session's pricing again (`getCheckoutSession`). With saved addresses the kept order's address (on a retry), else the primary one, else the first is preselected, and a failed validation is shown at the delivery step and the "Pay now" button (UX-02). The payment-failed page finds the kept order's cart with `PendingOrder.findCartId` and offers "Retry payment" (FR-0.12). The thank-you page never shows success without PAID: a missing order or one still unpaid after polling shows a terminal "not confirmed yet" state (RBUG-20). **PRD-014 Wave 1:** a ₹0 total is placed PAID by `completeCheckout` (COM-08; `COMPLETE_CHECKOUT` selects `pricing { total }`), so "Pay now" skips `createPaymentSession` and the provider, keeps no pending order and goes straight to thank-you; `SHIPPING_UNAVAILABLE` (no shipping zone covers the address) shows "We can't ship to this address yet" at the pricing step or at the "Pay now" button and scrolls to the delivery step so the shopper can pick or edit another address; a cart remove always sends the line's `variantId`, and a `VARIANT_REQUIRED` answer (COM-32) shows `REMOVE_ITEM_OVERRIDES` copy and refetches the bag.
- **HTML and JSON-LD.** Render CMS HTML only through `utils/sanitize-html.util.js` (every link gets `rel="noopener noreferrer"`; styles with a backslash are dropped, RSEC-11), and JSON-LD only through `toJsonLd` (`utils/json-ld.util.js`).
- **Shared files carry a "Keep in sync with `storefronts/rare-element/…`" header** (RMAINT-7): `redirect.util.js`, `pending-order.util.js`, `useVisitor.jsx`, the kit adapters and the others shared with rare-element. Change both.
- **Styling.**
  - Use global CSS files in `styles/` (plus the existing `*.module.css` where they're already used) and match the page you're in.
  - Don't add MUI, styled-components, emotion or Tailwind.
  - Fonts are declared with `@font-face` in `globals.css`.
- **Animation.**
  - Register GSAP plugins in the component that uses them, and clean up only your own timelines with `@gsap/react` `useGSAP` or a context revert. **Never** call `ScrollTrigger.killAll()` or `globalTimeline.clear()` (SF-20).
  - Smooth scroll is the single `SmoothScroller` (Lenis); don't create a second one, and resize it from a `ResizeObserver`, not an interval.
  - GSAP is the public `gsap` package; don't bring back `@gsap/business` or the `npm.greensock.com` registry (it no longer answers). `.npmrc` holds only the `GITHUB_TOKEN` reference; never put a token in it.
- **Consent first (PRD-014 FR-1.9, D10), on the kit.** `app/layout.jsx` runs only the kit's `CONSENT_DEFAULT_SCRIPT` (Consent Mode v2: every type "denied", then the stored choice). `components/common/ConsentBanner.jsx` (rendered by `Layout`) asks once (Accept all / Reject all / Manage: analytics, marketing) and saves through the kit's `updateConsent` ("marketing" is the kit's "ads"); the kit stores it (`zcom:consent`, no PII) and its `ZcomTags` loads GA + GTM only after "analytics" and the Meta Pixel + Google Ads tag only after "marketing"; nothing is requested from Google or Meta before that. The footer "Cookie Preferences" reopens it (the kit's `openConsentPreferences`). Never add a tag script yourself.
