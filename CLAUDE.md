## 0. Workspace rules (shared by every ZCommerce repo)

This repo is one part of the ZCommerce platform. The full map is in the workspace root `../CLAUDE.md` (`../../CLAUDE.md` for storefronts), when that file is present. The rules below are mandatory here even when it isn't.

1. **PRD first (tiered).**
   - **T1** covers: a new feature, page or module; a GraphQL contract change; a model or event change; auth, tenant, permission or billing logic; a new integration. T1 needs a PRD in `docs/prd/` with **Status: Approved** before any code. If none exists, draft one from `docs/prd/_TEMPLATE.md` (Status *Draft*) and **stop for approval**.
   - **T2** covers bug fixes, tweaks and small refactors. T2 needs only a line in `docs/changelog/YYYY-MM.md`.
   - Unsure of the tier? Treat it as T1 and ask.
   - Cross-repo PRDs have their source of truth in `zcom-backend/docs/prd/`; consumer repos keep a pointer PRD.
2. **Read docs before, update docs after (MANDATORY, no exceptions).** Documentation is part of the definition of done. Every change, including code, config, infra, dependencies and decisions, updates all related docs in the same change. Record decisions and approvals from conversation in the PRD or ADR immediately, before implementing. A task isn't finished while any doc disagrees with the code.
   - **Before** a change, read this file, `README.md`, `docs/README.md`, and the relevant PRD, ADR and architecture docs.
   - **After** it, in the same change, update whatever is now stale: the README (setup, commands, env names), `docs/architecture/*` (contracts), PRD status and implementation log, the changelog, `docs/README.md` (the index), and this `CLAUDE.md` (rules and known issues).
   - End every task with a **"Docs impact"** line.
3. **Ask, don't guess.**
   - Ask one precise question, with options and a recommendation, when the request conflicts with a PRD, an ADR, this file, or the code.
   - Do the same when docs and code disagree, or when a change would affect a contract, a security or tenant boundary, the design system, dependencies or deployment.
   - Don't ask about things you can verify in the code yourself.
4. **Scoped and safe.**
   - No drive-by refactors or mass reformatting.
   - Don't add dependencies without asking.
   - Never commit, push, deploy or touch databases unless asked.
   - Never print or commit secrets or `.env` values, including the token embedded in `git remote -v`.
   - Report checks honestly, keeping pre-existing failures separate from new ones.
5. **Coding style: the owner's signature (mandatory).** Follow the workspace `CODING_STYLE.md` (`../CODING_STYLE.md`, or `../../CODING_STYLE.md` for storefronts). Its baseline is the `zcom-backend` style.
   - 2 spaces, double quotes, semicolons, trailing commas, 80 columns.
   - Named exports with barrel `index.ts` files (React page and component files are the exception: `export default X;` at the end).
   - File names are `kebab-case.role.ts`.
   - Static-class controllers and services, with `return await`.
   - `xEnum = {…} as const`; the `I` prefix only for Mongoose documents; `UPPER_SNAKE` constants with unit suffixes (`_MS`, `_DAYS`).
   - `GraphQLError` with `extensions.code`; one `createLogger({ service })` per module.
   - JSDoc module headers and `// ─── ` section dividers.

   **New files** follow it exactly. **Edits** keep the file's existing formatting; never reformat untouched code. When you commit, use Conventional Commits: `type(scope): summary (PRD-NNN)`.
6. **Storefront specifics.**
   - Use only backend operations listed in the storefront contract doc, and validate field-level.
   - The server computes money.
   - **Plumbing is the kit's** (`@zcom/storefront-kit`, kit PRD-002): the proxy, Apollo links, customer session, guest cart id, consent, tags, attribution, payment launch and return, server reads and security headers. Fix them in `../../zcom-storefront-kit` (every store gets the fix with the next tag), never with a local copy. When you fix the store's own shared logic (`utils/api-error.util.js`, `utils/sanitize-html.util.js`, `hooks/useVisitor.jsx`, the checkout view, the stores), check `../rare-element` for the same issue.

## 1. What this is

The **Deveshe Dreams** brand storefront: a custom-designed shopper site on ZCommerce, with home, products, lookbooks, cart, checkout (the store's payment app: Razorpay, Cashfree or PayU, PRD-011; Nimbbl until its 2026-11-15 shutdown, backend PRD-029 D1), login and profile.

**Stack:**
- Next.js 16 with the **App Router** (since 2026-11-11, ADR-001), React 19.3, **JavaScript**.
- Apollo Client 4, zustand 5, react-hook-form + zod 4.
- GSAP 3.15 from the public npm registry (every plugin free since 3.13) with ScrollTrigger, SplitText and ScrollToPlugin (`gsap/dist/*`).
- `lenis` 1.3 (its own `autoRaf` loop), Swiper 14, react-toastify, three 0.187 (only the contact `PhoneModal`, plain three.js loaded with `ssr: false`; `@react-three/fiber`, `drei` and `@gsap/react` were removed on 2026-11-12, unused). Package versions follow the shared table in kit PRD-002 §11 (D3).
- Phone fields: `libphonenumber-js` (owner-approved 2026-11-12, imported from `libphonenumber-js/min`) behind one `components/common/PhoneInput.jsx` (native country `<select>` + national number) and `utils/phone.util.js` (`isValidPhone`, `splitPhoneInput`, `formatPhoneE164`; twin of rare's); it replaced `react-international-phone` and `react-phone-input-2`. Forms keep `countryCode` ("+91") and the national digits, as before. Don't add another phone library.

MUI, emotion, styled-components (PRD-002 SF-21), `react-tooltip` and `cross-fetch` (re-audit RMAINT-9) were removed, and the lockfile is pruned.

**Integration status: on the current backend contract (PRD-002 WS-F2, 2026-10-14).**
- All 49 operations validate against the composed backend schema (2026-11-12, `validate:clients`, after merging the cleanup that removed the unused `customerLogin`, `customerLogout` and `customerRefreshToken` documents; PRD-041 removed `CustomerSignup`, the new guest checkout, code sign-in and status page use the kit's own documents, and checkout's news box reuses `SubscribeNewsletter`) (PRD-032 added 12 review operations and `sort` on `GetProductReviews`; PRD-020 FR-13 added `GetVariantAvailability`; PRD-015 FR-20 added `MyOrderDetail`, `CancelMyOrder`, `CreateReturnRequest` and `CancelMyReturnRequest`; PRD-014 FR-0.8/FR-0.9 added `getClientSideCategories` for the category listing and `getReviews` for the home reviews, and `pricing` on the checkout session; FR-2.8 added `SubscribeNewsletter`, `GetProductReviews` and `GetSitemapProducts`; round 2 added `issueGuestCartId` and `mergeGuestCart`; round 3 added `unsubscribeNewsletter` for the `/unsubscribe` page; PRD-003 FR-0.5 added `customerRequestPasswordReset` and `customerResetPassword` for `/forgot-password` and `/reset-password`). The backend builds the link from the tenant's **configured domain**, so that domain must serve this storefront or redirect keeping the query string (FIN-3; the owner checks it per tenant). The contract is `../../zcom-backend/docs/architecture/storefront-api-contract.md`.
- **Tenant by host** (the backend has no db-token, PRD-007): the browser calls same-origin `/v1/graphql`, which `src/proxy.js` (the kit's `createZcomMiddleware`, kit PRD-002 FR-4.1) proxies to `API_GATEWAY_URL`. The kit strips client `x-zcom-*`, `x-tenant-domain` and `x-forwarded-host` headers (VSEC-4) and the shopper's `Origin`/`Referer` (PRD-007 FR-8.2), and adds the **edge headers**: `x-zcom-client-ip`, `x-tenant-domain` and `x-zcom-edge-secret` (PRD-002 R2-C1). Without `NEXT_PUBLIC_TENANT_DOMAIN` the proxy fails closed (never an untenanted request). Server reads (the server pages `/`, `/shop`, `/shop/[categories]`, `/search`, `/blogs`, `/blogs/[slug]` and `/product/[slug]`, the sitemap; `lib/server-query.js` on the kit's `zcomFetch`) send the tenant and the edge secret but no `x-zcom-client-ip` (catalog reads), except `/pay/[token]`, which sends the shopper's IP (`getRequestClientIp`).

## 3. Rules

- **Routing (App Router since 2026-11-11, ADR-001).**
  - One `app/<route>/page.jsx` per route, a **server** file: `metadata` or `generateMetadata` (from the page's `meta` object through `lib/seo-metadata.util.js`; the canonical is the route's path or `meta.canonical`, never with a query), `<PageSchemas meta path />` for the JSON-LD, then the page's client view from `views/`.
  - A page that needs data reads it in a server-only loader (`lib/page-data/<name>.server.js`), returns `{ props }` or `{ notFound: true }`, is read once per request through React `cache()` (keyed by value) and sets `export const dynamic = "force-dynamic"`; unknown or unpublished products are `notFound()`.
  - Client code uses `next/navigation` (`useRouter`, `usePathname`, `useSearchParams`, `useParams`); a static page whose view calls `useSearchParams` wraps it in `<Suspense>`. Pages that read a link token once read `window.location` in their mount effect and drop it with `window.history.replaceState` (a shallow replace).
  - A server file never imports a "use client" file for a value (it gets a reference, not the value): shared constants live in plain modules (`components/listing/listing.constants.js`, `utils/search-term.util.js`).
  - Don't add `src/pages` back.
- **Data.**
  - Put gql documents in `graphql/queries` or `graphql/mutations` and export them through `graphql/index.jsx`. Don't write inline `gql` in components.
  - **One Apollo client, the kit's** (`ZcomSsrProvider` in `components/layouts/Providers.jsx`): the store's own `useQuery` / `useMutation` share it (`@apollo/client/react`), so never create another client or call the gateway by another URL. `context: { skipAuth: true }` sends a call anonymously. Server code reads through `lib/server-query.js` (`serverQuery`, or `createServerQueryClient()` for Apollo's `query()` shape), never a browser client.
  - **The edge secret stays on the server.** The kit reads `EDGE_SHARED_SECRET` only in the proxy and its server functions; import `@zcom/storefront-kit/server` and `lib/*.server.js` only from server files (server pages, route handlers, loaders), never from a "use client" file. Check `.next/static` for the secret after a build.
  - Show errors with `utils/api-error.util.js`, which branches on `extensions.reason` / `code`, never on message text. It maps the round 2 reasons too (`CHECKOUT_EXPIRED`, `RESERVATION_RELEASED`, `INVALID_QTY`, `TOO_MANY_LINES`, `ORDER_CANCELLED`, `INVALID_GUEST_ID`, `TENANT_NOT_FOUND`). Every `PROMOTION_*` reason has its own message (`getPromotionMessage`: the store's copy, else the kit's; `getErrorMessage`, `getKitKeyMessage` and `getAnyErrorMessage` all use it), never one generic "not valid".
  - The kit's error link: `TOKEN_EXPIRED`/`UNAUTHENTICATED` → refresh once and retry; `INVALID_AUTH_TOKEN`, `TENANT_MISMATCH` or a refused refresh → the session ends (`tokenManager.onSessionEnded`, the auth context shows "Your session has ended"); `TENANT_NOT_FOUND` → `onStoreUnavailable` (one "store unavailable" toast, PRD-002 R2-C5); `TENANT_SUSPENDED` → one reload a minute to the 503 page (PRD-018 FR-1.6). A refresh that fails for a transient reason (network, 5xx) doesn't log the shopper out (RBUG-19).
- **Auth and tokens.**
  - The kit owns the session (kit PRD-002 FR-4.1): the access token lives **in memory only** (the kit's `tokenManager`). The refresh token is the HttpOnly `__Host-zc_cust_rt` cookie (`zc_cust_rt` in dev); JavaScript never reads or writes it, and never selects `refreshToken` from a response.
  - Sign-in is the kit's `useCodeSignIn` (email code, also the sign-up, PRD-041 FR-12) followed by `AuthContext.completeCodeSignIn`; password login (FR-11) and logout go through `context/AuthContext.jsx` on the kit's `useAuth`: the kit refreshes single-flight, clears the Apollo store before the customer token is used, and merges the guest bag once (`mergeGuestCart`; `merge: "failed"` shows "Some items from your bag are no longer available."; an invalid guest id is dropped). Don't add storage keys.
  - The persisted `isLoggedIn` flag is only a hint that a cookie session may exist; the server decides.
  - The persisted auth store holds no PII (PRD-014 FE-12, as rare RSEC-11: `partialize` to `{ isLoggedIn, userId }` + a v1 migration that rewrites the old `user-data` entry without the profile); `context/AuthContext.jsx` reloads the profile from `getMyProfile` after a page reload.
  - The kit's `migrateLegacyStorage` moves the pre-kit keys once (the `user-data` sign-in hint, the `visitorId` guest bag, the `zc_consent` choice and the `zc_ad_clicks` click ids), so returning shoppers stay signed in and keep their bag and consent. The legacy JS `refresh_token` cookie is not forwarded (kit PRD-002 D10).
  - After login, redirect only through `utils/redirect.util.js`, never `router.back()`. It resolves `?next=` with `new URL` and keeps it only when it stays same-origin (backslashes and control characters rejected, RSEC-6); with no valid `next` the shopper goes to `/`.
- **Money and checkout.** The server computes every price and total; show `getCart` / checkout-session values. **Both checkouts run on the kit's `useCheckout()` (kit 1.1.0, backend PRD-041 FR-17):** the signed-in `CustomerCheckout` in `views/CheckoutView.jsx` with `start` → `pay` / `retryPayment`, the guest `components/checkout/GuestCheckout.jsx` with `startGuest` → `pay`. The store holds no checkout GraphQL documents: the kit opens `createCheckoutSessionFromCart` (with `buildAttribution()` / `buildCheckoutConsent()`, PRD-012, PRD-034), waits for RESERVED, `completeCheckout` (a ₹0 total is placed PAID, COM-08, no payment), `createPaymentSession`, opens the store's active payment app with `launchPayment` (Razorpay / Cashfree SDK windows, a redirect or the PayU or CCAvenue form post, only to the known payment hosts; Nimbbl until its 2026-11-15 shutdown through the store's `nimbbl_sonic`, registered in `components/layouts/Providers.jsx` with `registerNimbblCheckout`, backend PRD-029 D1), `verifyPayment`, then waits for PAID. It keeps the unpaid order for a retry in its `PendingOrderStore` (sessionStorage, this tab, 2 h; its fingerprint covers the cart, lines, email and both addresses, not the bag's coupon, so the store drops it on a coupon change: `isKeptOrderStale`, and the guest's cart-fingerprint effect). **One flow on both paths (owner, 2026-11-12):** a checkout session takes a 15-minute stock hold, so it is opened **only on an explicit shopper action** (PRD-014 W0V2-02): "Continue to payment" (validates the form, then `start` signed in or `startGuest`, waits for RESERVED), never on page load, a preselected address or typing. The summary and the shipping step then show the session's server `pricing`. "Pay now" (`pay()`) is enabled only while the session is reserved for exactly the bag, coupon and details on screen, the news box included (`getDetailsKey` / `isReservedFor` in `utils/checkout-kit.util.js`); otherwise it is disabled with "Continue to payment to see your final total", and any change needs "Continue to payment" again (the backend then replaces the session). Without pricing shipping reads "Calculated at payment" / "Calculating…" and the total "Total before shipping" (or "Estimated total" with free shipping), never as final. With a kept order (a closed window or a failed payment, also after a reload) its saved address is preselected (else the primary, else the first), its pricing shown, and "Continue to payment" then "Pay now" pays it again (the kit's `start` reuses it); after a closed window the button reads "Pay again" (`retryPayment`); changed details say a new order will be placed.
